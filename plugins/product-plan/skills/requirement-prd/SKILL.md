# Requirement PRD（需求期 PRD）

为**单个未上线需求**撰写需求期 PRD：主 PRD 描述当前生产环境，本文档描述**目标行为**——需求评审、开发对齐、上线后融入主 PRD 的信息载体。章节结构与表头固定规范，后期合并零转换。

## 定位边界

| | 需求期 PRD（本文档） | 主 PRD |
|---|---|---|
| 描述 | 目标行为：计划中，可变，允许待确认 | 当前生产行为：已上线、产品确认、唯一权威 |
| 位置 | `docs/requirements/` 或任务系统工作项 | 项目的主 PRD 目录 |
| 生命周期 | 上线合并后移入 `archive/` 归档只读，此后修改只发生在主 PRD | 持续维护 |

## 状态门槛——先判断再动手

- **需求未上线 / 未开放** → 本技能适用；灰度、内测、白名单开放等中间态仍属需求期，按实际生效范围在文档中写明。
- **已在生产环境正式生效并经产品确认** → 拒绝新建需求文档：行为已属主 PRD，直接更新主 PRD（走项目的主 PRD 维护流程）。
- **意图是修改已上线功能** → 增量变更可用本技能写需求文档，但不得借此绕过"上线后融入主 PRD"的纪律。
- 说不清属于哪种 → 问用户，不要替用户假设。

## 工作流

### 1. 收集输入

- **已有对话上下文优先综合**，不重复访谈；缺口一次一批补问（系统化澄清适合先走 interview-me / grilling，本技能承接其产出）。
- 项目已有结构化 PRD 体系（含全局规范与功能文档）时**先读归属文档再动笔**：术语表、枚举与数据字典、权限规范、全局业务规则、相邻功能文档——需求文档**引用**权威定义，不复制、不重定义、不发明新说法。
- 无体系也可使用：就地澄清业务规则后落笔，产出的文档将来就是建立体系的输入素材。

### 2. 定形态、列归属

动笔前先列**归属清单**：本需求涉及的每类定义各由哪份文档承载；归属清单是工作过程产物，不进需求文档正文。按需求形态选择骨架，可组合：

| 需求形态 | 骨架 |
|---|---|
| 单功能需求（默认） | 功能级骨架（见第 3 步） |
| 跨模块流程需求（多个模块按交接条件协同才闭环） | 跨模块流程骨架（见第 3 步）；各模块自身行为变化叠加各自的功能级骨架——本模块能独立说清的行为不塞进流程文档 |
| 引入全局定义（新角色 / 术语 / 枚举与跨模块字段 / 全局规则 / 通用权限 / 数据对象） | 附「全局定义增量」章节，按对应增量表结构起草拟新增条目，标注建议归属——融合时进对应全局规范文档，不并入功能文档 |
| 横切通用能力（如所有列表统一加导出、全局分页规则调整） | 附「通用功能增量」章节，按通用功能表结构起草，融合时进通用功能规范 |
| 开辟新业务模块 | 附模块概述骨架 + 首批功能的功能级骨架；模块清单与索引登记交由主 PRD 维护流程 |

兜底规则：未覆盖的体系级调整（产品定位与范围边界等）不进需求文档，在归属清单中标注，交由主 PRD 维护流程处理。

### 3. 撰写文档

结构三段，前两段合并时丢弃，第三段是文档主体：

1. **元信息头**：需求来源（任务系统链接 / 提出人）、状态（草稿 / 评审中 / 已确认 / 开发中；上线合并后整篇归档只读，状态不再更新）、目标版本。
2. **背景与动机**：一节说清为什么做。**不含** KPI、风险评估、路线图（MVP→v1.1→v2）——立项评估类内容留在任务系统，不进需求文档。
3. **主体骨架**：按第 2 步选定的形态套用。

**功能级骨架**（按功能类型裁剪：单据 / 审批 / 查询 / 配置 / 自动处理 / 集成——如查询类通常裁掉状态管理；无内容的章节整节删除，不留空壳）：

- **1 功能概述**：功能说明；使用角色（角色｜业务职责）；功能范围（含 / 不包含，**Non-Goals 必填**——合理但明确不做的能力附一句话理由）；取舍记录（按需：备选方案｜未采纳原因）。
- **2 业务流程**：前置条件；正常流程（每步标注执行者：用户 / 角色、系统、定时任务）；分支流程（分支条件：对应处理）；流程图（按需，Mermaid）。
- **3 功能详细说明**：功能操作（操作｜触发方式｜前置条件｜处理结果）；页面与交互按页面类型——列表页（默认排序、组合逻辑、列｜取值口径、筛选参数｜匹配方式），详情页（区块｜内容、状态联动逐条、关联内容），表单页（分组｜字段呈现顺序、按钮组、提交去向），看板统计页（时间范围、指标计算口径、图表｜类型与数据、下钻入口）；**字段定义（字段｜含义｜是否必填｜编辑条件｜校验规则｜默认值/生成规则）**，展示字段注明取值口径（实时 / 快照 / 计算公式写分子分母）；非功能性要求与渠道差异（按需）。
- **4 业务规则**：每条按触发条件 / 处理规则 / 处理结果表述；简单规则合并为一条完整表述，不为凑三段式而换说法重复。
- **5 状态管理**（按需）：状态定义（状态｜业务含义｜是否终态｜允许操作）；状态转换（当前状态｜触发操作｜转换条件｜目标状态）；初始状态与终态后数据处理。
- **6 权限控制**：操作｜允许角色或权限｜数据范围｜限制条件｜无权限表现（按钮隐藏 / 置灰 / 点击提示）。
- **7 异常与边界处理**：场景｜触发条件｜系统处理。重点覆盖数据不存在或已变化、重复提交、并发修改、不符合业务规则、依赖对象状态异常、外部服务失败；涉及外部处理、异步操作或资金的按**结果维度穷举闭环**——成功 / 拒绝 / 超时 / 重复 / 取消 / 部分完成，每种结果说明状态去向、数据影响、用户反馈与后续处理主体，**不得用「系统处理」「人工处理」等模糊表述代替规则**。
- **8 关联业务行为**（按需）：触发行为｜时机（同步 / 异步 / 定时）｜关联模块或对象｜业务结果（含操作留痕与审计日志）。
- **9 业务验收场景**：场景｜前置条件｜操作｜预期结果。核心场景 3～8 个，边界值优先（零值、恰好上限、重复请求、并发提交、部分完成、失败恢复）。

**跨模块流程骨架**：流程概述；业务流程图；流程步骤（步骤｜负责模块｜触发条件｜业务操作｜输出结果）；跨模块交接规则（逐交接环节写交接条件）；异常与补偿流程（异常场景｜影响模块｜处理规则）；核心业务对象流转（业务对象｜创建模块｜关联模块｜流转规则）；关联需求文档（本批各模块的功能级需求文档；项目既有体系的相关功能文档另列引用，不复制其规则）。

**增量表结构**（起草拟新增条目用，表头与全局规范惯例一致）：角色：角色｜角色定位｜主要业务职责｜适用主体；术语：术语｜业务定义｜别名或说明；数据字典——对象（对象｜业务含义｜归属模块｜关联对象）、字段（字段｜业务含义｜类型｜约束）、枚举（枚举名称｜枚举值｜业务含义）；权限：权限类型｜定义｜控制范围，数据范围｜定义｜适用条件；全局规则：规则编号｜规则名称｜适用范围，附规则详细定义；通用功能：功能｜统一适用范围｜详细规则；模块概述：模块定位、业务范围、功能清单（功能｜核心能力｜文档路径）、核心业务对象（对象｜业务含义｜关联功能）、主要业务流程、模块依赖关系（关联模块｜关系说明）、关联全局规范。

写作纪律：

- 行为级章节写**目标行为**——"上线后系统应该怎样"，以业务行为表述；不写实现方案 diff，不引用具体代码文件与函数。
- **验收场景必须可衡量、可推演**：每个场景按正文规则推出唯一结果；拒绝"快、好用、直观"，写具体数值、口径与边界。
- 拿不准的规则**不臆造**：写 `<!-- 待确认：原因 -->` 标记，并在文末汇总待确认清单供评审逐条裁决。
- **Non-Goals 必填**：防止范围蔓延、防止"没写的"被误读为"待补充"。
- 同一请求存在多种合理解释时问用户，不静默选择一种。

### 4. 存放与迭代

- 默认 `docs/requirements/<MM-DD>-<需求标识>.md`（进行中的需求直接放需求目录下，`MM-DD-` 日期前缀使文件按时间自然排序；用户指定位置从其指定）；使用云效 Projex 等任务系统时，正文贴入工作项描述。
- **禁止写入主 PRD 目录**——主 PRD 只描述生产环境，本文档未上线前不入内。
- 同一需求迭代**直接改同一文件**，不建 `-v2` / `-final` 副本；历史交给 Git。
- **归档**：上线合并后把文件移入 `docs/requirements/archive/<YYYY-MM>/`（文件名不变，按月分目录）。进行中需求看需求目录根，历史需求看 `archive/`。

### 5. 自检（交付前）

- 结构对照所选骨架：该功能类型重点章节齐全；合法裁剪的章节已整节删除，不留空壳与占位符；Non-Goals 已填写。
- 验收场景逐条可推演出唯一结果；异常与边界场景无模糊表述——模糊即规则缺失，回正文补规则。
- 待确认标记已全部汇总到文末清单；术语与项目已有术语体系一致。
- 全局性内容（枚举、权限、通用规则）是引用权威定义而非本地复制——本地复制将来会在合并时制造重复定义。

## AI 纪律

- **本文档不是主 PRD**：任何内容不得直接写入主 PRD；用户要求"写进 PRD"时先按状态门槛判断，未上线一律留在本文档。
- **区分目标与现状**：开发任务中本文档（目标行为）与主 PRD（当前行为）对照理解差异；两者冲突不是文档错误，而是待实现的变更本身。
- **待确认标记必须求证**：检索到 `<!-- 待确认：... -->` 时向用户求证，禁止自行补全后当作已确认结论。
- **修改须经人审核**：正式业务规则的确认由产品负责（个人项目即用户本人），不以代码实现单方断定需求。
