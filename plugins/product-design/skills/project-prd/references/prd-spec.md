# 大型软件项目 PRD 管理规范

版本：V1.0

## 一、管理目标

建立一套结构清晰、持续维护、方便检索、支持 Git 版本管理及 AI 辅助开发的产品需求文档（PRD）体系。

核心目标：

1. **单一事实来源**：主 PRD 是当前生产环境正式产品需求的唯一权威来源。
2. **模块化管理**：按照产品业务能力组织文档，避免单一 PRD 过度膨胀。
3. **增量开发、持续合并**：新需求在外部任务系统中管理，上线后将最终需求融入主 PRD。
4. **历史版本可追溯**：通过 Git Commit 和 Tag 管理历史，不在 PRD 中重复维护版本文档。
5. **避免信息冗余**：业务规则、流程和功能定义尽可能只维护一份。
6. **AI 友好**：文档结构、命名和内容规范应便于 AI Agent 按需检索、理解和引用。

## 二、核心管理原则

### 2.1 主 PRD 只描述生产环境

主 PRD 定义为：**当前生产环境已经上线、实际生效且经过产品确认的完整功能与业务规则。**

不包含：

- 尚未批准或计划中的需求。
- 正在设计、开发或测试的需求。
- 尚未实际生效的功能。
- 需求讨论、开发任务及过程记录。
- 历史版本的完整 PRD 副本。

已部署但尚未开放的功能，不视为正式上线功能。对于灰度发布的功能，应明确实际生效的用户范围及适用条件。

对于生产环境中的缺陷，不应直接把错误行为写成正式需求，应记录在缺陷管理系统中并推动修复。

### 2.2 主 PRD 采用持续更新模式

不因每次迭代创建新的主 PRD。

例如：

- 采购订单功能始终由 `orders.md` 描述。
- 新增订单撤销能力后，修改 `orders.md` 中对应的功能和规则。
- 原有规则发生变化时，直接更新对应内容，而不是追加一份新旧规则对照说明。
- 功能正式下线后，删除或调整不再生效的定义。

主 PRD 始终保持当前、完整、一致，不承担历史记录职责。

### 2.3 增量需求与正式 PRD 分离

| 内容 | 管理位置 | 主要职责 |
|---|---|---|
| 正式主 PRD | `prd/` | 当前生产环境的完整需求定义 |
| 新增及变更需求 | 外部任务系统 | 待开发、开发中、测试中的需求及过程 |

增量需求可以有独立的需求说明，但不在 `prd/` 中建立专门的 `changes/` 目录。

正式上线后，将增量需求中最终生效的内容融合到对应主 PRD，而不是将原始需求文档整篇复制进去。

## 三、PRD 目录架构

四个逻辑层级：

| 层级 | 目录 | 职责 |
|---|---|---|
| L1 | `00-overview/` | 产品整体定位、能力范围和角色体系 |
| L2 | `01-foundation/` | 全产品共享的业务规则和基础定义 |
| L3 | `02-modules/` | 各业务模块及具体功能 PRD |
| L4 | `03-workflows/` | 跨业务模块的端到端流程 |

### 3.1 标准目录结构

PRD 目录默认位于目标项目仓库根的 `docs/` 下（即 `docs/prd/`），团队可另行指定位置；若文档独立成仓则位于文档仓库根。全文以 `prd/` 简称该目录。

```text
prd/
├── index.md                     # PRD 总入口
│
├── 00-overview/                 # 产品总览
│   ├── product.md               # 产品定位与范围
│   ├── modules.md               # 产品功能模块地图
│   └── roles.md                 # 用户角色与业务主体
│
├── 01-foundation/               # 全局规范
│   ├── terminology.md           # 业务术语
│   ├── permissions.md           # 权限及数据隔离规则
│   ├── business-rules.md        # 全局业务规则
│   ├── data-dictionary.md       # 核心业务数据字典
│   └── common-features.md       # 通用功能规范
│
├── 02-modules/                  # 业务模块
│   ├── procurement/             # 采购管理（示例）
│   │   ├── overview.md           # 模块概述与导航
│   │   ├── orders.md            # 采购订单
│   │   ├── approval.md          # 采购审批
│   │   └── returns.md           # 采购退货
│   ├── warehouse/               # 仓储管理（示例）
│   │   ├── overview.md
│   │   ├── inbound.md           # 入库管理
│   │   ├── outbound.md          # 出库管理
│   │   └── inventory.md         # 库存管理
│   └── ...
│
└── 03-workflows/                # 跨模块业务流程
    ├── procure-to-pay.md        # 采购到付款
    └── order-to-settlement.md   # 订单到结算
```

以上模块仅为示例，具体模块根据项目业务架构确定。不设置 `changes/`、`releases/`、`decisions/` 等目录。

### 3.2 各目录职责

**00-overview：产品总览**——描述产品整体定位、业务边界、业务能力地图，以及用户角色和业务主体。不重复详细功能需求。

**01-foundation：全局规范**——集中管理跨模块通用的定义：术语、角色权限、数据隔离、通用业务规则和核心数据字典。遵循单一权威定义原则：全局规则集中定义，各模块通过链接引用。

**02-modules：模块 PRD**——整个文档体系的核心，按业务能力组织。每个模块包含一个 `overview.md` 及必要的功能级 PRD。模块 `overview.md` 负责描述模块定位、功能清单、业务边界及其他模块依赖，不承载完整的功能需求细节。

**03-workflows：跨模块流程**——描述业务模块之间的端到端协同关系。只定义跨模块流程、交接条件和业务关系，具体功能规则引用对应模块 PRD，不重复描述。

## 四、文档拆分规范

### 4.1 以业务模块为主要组织依据

文档目录应反映产品的业务能力结构，而不是研发团队、开发迭代或软件版本。

原则上：

- 一个业务模块对应一个模块目录。
- 一个复杂且相对独立的功能对应一份功能 PRD。
- 简单且高度关联的功能允许合并在同一文档。
- 当单个功能复杂度显著增加时，再拆分子功能文档。

不要求所有按钮、接口或字段都建立独立的 PRD 文件。

### 4.2 拆分判断标准

出现以下情况时，优先考虑拆分：

- 具有相对独立的业务流程。
- 包含复杂状态流转或业务校验。
- 存在较多独立的业务规则和异常场景。
- 功能可以独立理解、评审或维护。
- 单份文档过长，已经明显影响检索和维护。

拆分时优先保持业务内容的完整性，不单纯根据文档行数或篇幅机械拆分。

### 4.3 避免重复定义

**业务规则归属唯一、跨模块引用复用、不同文档职责清晰。**

例如：采购订单 PRD 定义采购订单的创建、审核和状态规则；入库管理 PRD 定义采购入库的操作与库存变化规则；采购到入库的跨模块流程文档描述两者如何协同。三份文档不重复维护同一套详细审批或入库规则。

归属细则：**枚举编码由数据字典权威维护，状态转换由功能 PRD 权威维护**——跨模块流程与模块概述不得出现完整状态机或枚举清单的副本，只写引用入口与交接条件。

## 五、PRD 内容规范

### 5.1 模块 overview

建议包含：

1. 模块定位与职责。
2. 业务范围与边界。
3. 功能清单及文档链接。
4. 核心业务对象与模块关系。
5. 主要业务流程简述。
6. 关联跨模块流程。
7. 相关全局规范链接。

### 5.2 功能 PRD

统一结构（章节模板见 [templates/11-feature-prd.md](templates/11-feature-prd.md)，按功能类型裁剪，裁剪表见 [templates/README.md](templates/README.md)）：

| 章节 | 内容 |
|---|---|
| 1. 功能概述 | 功能说明、使用角色、功能范围（含 Non-Goals 不做清单）、取舍记录（按需） |
| 2. 业务流程 | 前置条件、正常流程、分支流程、流程图（按需） |
| 3. 功能详细说明 | 功能操作、页面与交互（按需）、字段定义、非功能性要求（按需） |
| 4. 业务规则 | 触发条件、处理规则、处理结果 |
| 5. 状态管理（按需） | 状态定义、转换条件与限制 |
| 6. 权限控制 | 功能权限、数据权限及角色差异 |
| 7. 异常与边界处理 | 边界条件、冲突场景和处理规则 |
| 8. 关联业务行为（按需） | 对其他业务对象或模块的影响 |
| 9. 业务验收场景 | 关键路径与高风险边界的可验证实例（核心 3～8 个，不复述规则） |
| 10. 关联文档 | 相关模块、全局规范及跨模块流程 |

没有对应内容的章节可以省略，不强制所有 PRD 使用完全相同的篇幅和结构。

功能 PRD 应以**业务行为和产品规则**为核心。描述深度判据：**开发和测试读完正文及其权威引用后，能确定业务结果、无需自行补规则；实现方式仍允许研发选择。**

把握五条原则：

- **业务行为写细**：谁能操作、何时允许、输入约束、状态变化、资金或数据影响、失败后的去向。
- **交互写到可验收**：按钮显隐、确认提示、错误反馈、刷新与跳转等影响用户操作的行为要写；视觉样式引用设计稿。
- **外部契约写准确**：金额精度、超时、重试、接口参数，凡影响收费、重复处理或第三方接入的就是必要需求，不能删。
- **内部实现按需下沉**：类名、函数名、行锁方式、递增标记、缓存容器等交给技术设计；实现机制写成业务约束——如"递增代次标记"应表述为"较早请求的响应不得覆盖较新查询结果"。
- **公共规则用引用复用**：功能文档写本功能如何触发规则及产生什么结果，不再次完整定义规则本身。

关键需求可使用稳定的需求 ID，以支持任务与测试追踪；但不应因此在主 PRD 中重复记录整个任务生命周期。

## 六、需求开发与 PRD 更新流程

### 6.1 标准流程

**阶段一：需求设计**——在外部任务系统中创建新需求，完成需求说明、评审和确认。主 PRD 保持不变。

**阶段二：开发与测试**——研发根据已批准的增量需求实现功能，测试人员验证预期行为。开发过程中如发生需求调整，在任务系统中完成评审与修订。主 PRD 仍然保持不变。

**阶段三：生产发布**——将功能部署到生产环境，确认功能实际生效，并完成必要的上线验证。

**阶段四：更新主 PRD**——根据最终上线并确认的业务行为：

1. 找到对应的模块或功能 PRD。
2. 将新增功能融入现有章节。
3. 修改已经变化的规则、流程和状态。
4. 移除不再适用的功能描述。
5. 检查是否影响全局规则和跨模块流程。
6. 通过 Git Pull Request 完成文档审查和合并。

**阶段五：冻结版本基线**——完成生产验证和文档同步后，使用 Git Tag 保存对应生产版本的文档快照。

如果功能上线失败或发生回滚，应根据实际生效状态修正 PRD，不保留未成功发布的功能定义。

### 6.2 更新时机约束

| 阶段 | 更新主 PRD |
|---|---|
| 需求提出 | 否 |
| 需求评审通过 | 否 |
| 开发完成 | 否 |
| 测试通过 | 否 |
| 已部署但功能未开放 | 否 |
| 生产环境正式生效 | 是 |
| 已发布功能发生规则调整 | 是 |
| 正式功能下线 | 是 |

主 PRD 更新应作为上线交付的必要环节，避免功能发布后长期没有同步文档。

### 6.3 跨模块变更

一个需求可能同时影响多个模块。例如采购订单审核逻辑变化，可能影响采购管理、仓储入库和财务结算。这种情况下，必须检查所有受影响的功能 PRD、全局规则和跨模块流程，不允许只修改发起需求的模块而遗漏其他依赖模块。

## 七、Git 版本管理规范

### 7.1 Git 负责历史版本

不在 PRD 中通过文件名管理版本。

不推荐：`orders-v1.md`、`orders-v2.md`、`orders-final.md`、`orders-latest.md`。

推荐始终使用：`02-modules/procurement/orders.md`。

通过 Git Commit 记录内容变动，通过 Git Tag 保存正式生产版本的文档快照。

### 7.2 文档合并原则

- 主 PRD 的变更必须经过审查。
- 文档修改应与已经确认的生产行为一致。
- 不得提前将未来版本需求合入当前生产版本的主 PRD。
- 通过 Git Diff 识别修改内容，通过 Git 历史追溯规则变动。
- Git Tag 对应的文档快照应与其标识的生产版本一致。

如果 PRD 和代码分别位于不同 Git 仓库，应维护可查询的版本或 Commit 对应关系，避免出现代码与文档版本不匹配的问题。

## 八、AI Agent 使用规范

主 PRD 也是 Codex、Claude Code 等 AI Agent 理解现有产品的基础材料。

### 8.1 按需读取

AI Agent 应优先读取：根目录 `index.md` 定位模块 → 相关模块 `overview.md` 确定功能边界 → 目标功能 PRD 理解业务规则 → 必要的全局规范与跨模块流程。不要求每次任务都加载完整 PRD 目录。

### 8.2 区分当前行为与目标行为

AI Agent 执行开发任务时：

- 主 PRD 表示当前生产环境的正式需求。
- 外部任务描述本次需要实现的增量变化。
- 两者共同用于理解当前状态与目标状态的差异。
- AI 不得将尚未上线的需求直接写入正式主 PRD。

### 8.3 协助维护

AI Agent 可以辅助：识别需求变更影响的文档范围、检查不同 PRD 之间的规则冲突、将已发布增量需求整合到主 PRD、检查文档链接与术语一致性、对照代码与测试结果发现文档遗漏。

AI 生成的修改必须经过审核，不能仅凭代码实现自动认定所有行为都是正确的产品需求。

## 九、文档质量管理

| 检查项目 | 验收要求 |
|---|---|
| 准确性 | 与当前正式生产行为一致 |
| 完整性 | 关键流程、规则、状态及异常场景有明确说明 |
| 一致性 | 不存在相互矛盾的业务规则 |
| 唯一性 | 同一业务规则有唯一权威定义 |
| 可检索性 | 目录、文件名和索引清晰 |
| 可追溯性 | 通过 Git 查询修改及历史基线 |
| 时效性 | 功能正式发布后同步更新对应 PRD |
| 可维护性 | 文档粒度合理，避免过度拆分及重复内容 |

建议为每个业务模块明确一名文档负责人，由其负责审核本模块 PRD 的准确性与完整性。研发、测试人员可以提出修订，但涉及正式业务规则的修改，应由相应产品负责人确认。个人项目或小团队中，产品确认与文档负责人由用户本人承担。

审查结论分级：机械检查（链接、索引、占位符、结构体量）通过不等于文档质量审查通过。语义复核以业务对象为轴横向核对各文档表述（能力范围、编码、权限、状态、公式），发现的问题按直接矛盾、条件未说明、定义缺失、示例错误、重复定义五类记录，每项附具体证据场景。

## 十、最终管理约定

1. **主 PRD 只描述当前生产环境**——不承担需求计划、开发过程和历史版本管理职责。
2. **PRD 按业务模块组织**——产品总览、全局规范、业务模块和跨模块流程四层结构。
3. **增量需求在外部管理**——开发完成并正式上线后，将最终业务规则融入主 PRD。
4. **不在 PRD 中重复维护历史**——Git Commit 和 Tag 负责历史追溯和生产版本基线。
5. **避免重复与过度拆分**——相同规则只定义一次，保持文档结构稳定、内容完整、维护成本可控。
6. **AI 可以协助，但不能绕过评审**——AI Agent 辅助文档分析、维护和验证，正式业务规则仍需通过产品确认。

**管理模式**：主 PRD 负责定义当前产品，外部任务系统负责管理产品变化，Git 负责管理历史，AI Agent 负责辅助理解和维护。`prd/` 始终是一套结构化、完整、可追溯且与当前生产环境一致的正式产品需求文档。
