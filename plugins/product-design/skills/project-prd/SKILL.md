# Project PRD

在软件项目中建立并持续维护一套产品需求文档（PRD）体系。主 PRD 是**当前生产环境正式产品需求的唯一权威来源**：已上线、实际生效、经过产品确认的完整功能与业务规则。参考资料按需读取：完整管理规范见 [references/prd-spec.md](references/prd-spec.md)（本文件是工作流速查，细节拿不准时读规范原文）；12 类文档模板见 [references/templates/](references/templates/)（初始化或撰写文档时套用，入口 [references/templates/README.md](references/templates/README.md)）。

## 核心原则

1. **主 PRD 只描述生产环境。** 计划中、开发中、测试中、已部署未开放的需求一律不入主 PRD。
2. **持续更新，不做版本副本。** 采购订单永远由 `02-modules/procurement/orders.md` 描述：规则变了直接改对应内容，功能下线直接删。禁止 `orders-v2.md`、`orders-final.md` 这类文件名。
3. **增量需求在外部任务系统。** 主 PRD 不设 `changes/`、`releases/`、`decisions/` 目录；需求上线确认后才融入。
4. **Git 负责历史。** Commit 记内容变动，Tag 存生产版本基线快照；文档自身不重复维护历史。
5. **规则唯一权威。** 全局规则在 `01-foundation/` 定义一次，各模块链接引用；跨模块流程只写协同与交接条件，不复制功能规则。

## 该不该写入——先判断再动手

用户要求把某内容写进主 PRD 时，先判断状态（权威定义见规范 2.1，此处为速查分支）：

- **已在生产环境正式生效**并经产品确认 → 写入，走工作流 B。
- **未上线 / 未确认 / 开发测试中** → 拒绝写入主 PRD，说明规范（主 PRD 只描述生产环境），建议留在外部任务系统。
- **灰度发布** → 可写入，但必须明确实际生效的用户范围及适用条件。
- **生产缺陷的错误行为** → 不写成需求，提示记录到缺陷管理系统并推动修复。
- **立项/评估类内容**（机会评估、PR/FAQ、go/no-go 结论）→ 不入主 PRD，属外部任务系统阶段；主 PRD 只接收最终生效的行为。

## 工作流

### A. 初始化 prd/ 体系

适用：项目还没有 PRD 目录，或现有文档结构不符合规范。

1. 侦察：读现有文档、代码结构，与用户对话，摸清业务模块、用户角色、核心术语。模块划分按实际业务能力定，不照抄示例目录，**划分方案先与用户对齐再动工**。项目已有设计文档或旧 PRD 时，按本体系模板结构重组迁移而非原样搬运，无把握处标注待确认。
2. 确定位置：默认在目标项目仓库根的 `docs/prd/` 创建（用户另行指定位置时从其指定；若文档独立成仓则放文档仓库根，并维护与代码仓库的版本对应关系），四层骨架（模块按实际业务定，不照抄示例）：

   ```text
   prd/
   ├── index.md               # 总入口：模块地图 + 按需读取指引
   ├── 00-overview/           # product.md 定位与范围 / modules.md 模块地图 / roles.md 角色体系
   ├── 01-foundation/         # terminology / permissions / business-rules / data-dictionary / common-features
   ├── 02-modules/<模块>/     # overview.md 模块概述 + 功能级 PRD
   └── 03-workflows/          # 跨模块端到端流程
   ```

3. 写作前置——归属清单：动笔前先明确本次涉及的每类定义各由哪份文档权威承载（概念 → terminology、枚举与跨模块字段 → data-dictionary、权限 → permissions、全局规则 → business-rules、状态机与功能规则 → 功能 PRD、跨模块协同 → workflow）。归属不清的先定归属再写；归属表是工作过程产物，不进 `prd/` 目录。
4. 套用 [references/templates/](references/templates/) 中对应的文档模板撰写各文件（模板索引见其 README）。纪律：模板是结构参考不是必填表格——「按需」章节没有内容直接删除；总览与模块 overview 轻量化、全局规范与跨模块流程规则化、功能级 PRD 精细化；功能级 PRD 按功能类型（单据/审批/查询/配置/自动处理/集成）裁剪章节，第 3～9 章是 AI 理解系统的重点。
5. 填充顺序：先根 `index.md` 与 `00-overview/product.md`，再按项目实际需要补 foundation 与 modules。没有把握的业务规则问用户，或统一用 `<!-- 待确认：原因 -->` 标记，**不臆造**。暂无内容的层（如还没有跨模块流程）可先不建目录——Git 不跟踪空目录，首次有内容时再建。
6. 运行 [scripts/prd-check.py](scripts/prd-check.py)（`python3 scripts/prd-check.py <prd目录>`）确认无 ERROR 后，Git commit 提交骨架与初始内容。

### B. 融合已上线需求（上线后更新）

适用：功能已部署到生产、验证生效并经产品确认。开发与测试阶段一律不动主 PRD。功能正式下线同样走本工作流：删除对应功能文档，并同步清理模块 overview 索引行、跨模块流程与其他 PRD 中的引用，不留悬空链接。

1. 定位受影响文档：目标模块功能 PRD + 可能受影响的全局规范与跨模块流程，从 `00-overview/modules.md` 的依赖关系表与 `03-workflows/` 流程文档定位受影响模块。**跨模块变更必须逐一检查所有依赖模块**（例：采购订单审核逻辑变化，同时查采购、仓储入库、结算），不允许只改发起需求的模块。
2. 融合而非粘贴。动笔前先列归属清单：本次涉及的枚举、字段、权限、全局规则各由哪份文档权威定义，归属清晰的才写正文，跨文档只写引用、交接与渠道差异。把最终生效的行为融入现有章节——修改变化的规则、删除不再生效的描述。不整篇复制原始需求文档，不追加新旧规则对照说明。全新功能文档按功能级 PRD 模板（[references/templates/11-feature-prd.md](references/templates/11-feature-prd.md)）创建，并按功能类型裁剪章节（裁剪表见 [references/templates/README.md](references/templates/README.md)）；需求引入新的跨模块流程时按跨模块流程模板（[references/templates/12-workflow.md](references/templates/12-workflow.md)）创建；**新建文件须同时在所属模块 overview 的功能清单表登记索引行**。
3. 提交前门禁：先运行 [scripts/prd-check.py](scripts/prd-check.py) 做机械检查——**ERROR 必须清零或经用户明确确认豁免**（悬空链接、索引未登记、占位符与指引残留、待确认标记），WARN 逐条人工确认；再逐项核对：受影响模块 PRD 已全部更新（含跨模块依赖）；涉及的数据字典与术语表已同步；状态机与验收场景已与生产实际行为核对；触碰的全局规则已在 `01-foundation/` 更新或确认无影响；新建功能已在模块 overview 功能清单登记、下线功能的引用已清理；`<!-- 待确认 -->` 标记已清零或经用户确认保留。
4. Git Pull Request 提交审查。功能上线失败或回滚时，按实际生效状态修正 PRD，不保留未发布成功的功能定义。
5. 重大版本可在产品确认后打 Git Tag 固化文档基线，Tag 须与其标识的生产版本一致。

### C. PRD 质量检查

适用：用户要求检查 / 评审 PRD，或每次更新后的自查。

先运行 [scripts/prd-check.py](scripts/prd-check.py) 做机械检查（结构漂移、悬空链接、索引登记、占位符与指引残留、文档体量与结构嫌疑），把 ERROR 清零、WARN 汇入问题清单；再按下表做语义检查。

检查表（完整验收标准见规范第九章）：准确性（与当前生产行为一致）、完整性（关键流程、规则、状态、异常场景有说明；**对照模板 11 十章结构与裁剪表——缺失章节属于该功能类型「重点描述」或「必答项」的列为问题，属合法裁剪的不报**；复杂业务边界有失败去向——状态、额度或数据影响、重试主体、重复操作的结果）、一致性（无相互矛盾规则）、唯一性（同一规则只有一处权威定义）、可检索性（目录、命名、索引清晰，引用完整——相对链接有效、模块 overview 功能清单与实际文件一致；**结构形态对齐——保留章节的命名、层级与章节内骨架须与模板一致：要素齐备（如列表页的排序/组合逻辑/列表/筛选）、表结构同构（表头列与模板一致，如字段定义六列、状态定义含是否终态、权限含无权限表现、触发行为含时机），自定义节名或残缺表列视为结构漂移，重组时内容保留、结构映射**）、可追溯性（可通过 Git 查询修改与版本基线）、时效性（已上线功能已同步）、可维护性（文档粒度合理，无过度拆分与重复；**功能细节未混入模块 overview**——混入的拆为独立功能 PRD 文件）。

检查手段界定：一致性、唯一性、可检索性、可维护性可纯文档内自查；准确性、完整性、时效性需结合生产信息或向用户求证，不由代码实现单方断定。一致性复核以**业务对象为轴**而非文件轴：对核心业务对象，横向核对它在总览、字典、功能、渠道、流程各文档中的能力范围与支持条件、术语与枚举编码、权限与凭证生命周期、状态转换与终态例外、金额公式与时间窗口及唯一性范围是否一致；同时检查"链接目标存在但缺少被引用内容"的语义死链。

输出问题清单（文件 + 位置 + 类型 + 问题 + 证据场景 + 建议），经用户确认后再修改。类型分五类：**直接矛盾 / 条件未说明 / 定义缺失 / 示例错误 / 重复定义**；每项附具体证据场景，可相容的规则不判为冲突。两份文档表述冲突时不得默认更详细的一份为准、不得按模板惯例补齐——列为待确认项交产品裁决。机械检查通过不等于质量审查通过，结论分两级表述。

## AI 纪律

- **区分当前与目标**：主 PRD 表示当前生产状态，外部任务描述本次增量变化；开发任务中两者对照理解差异，但永远不把任务系统里的需求直接写进主 PRD。
- **按需读取**（完整顺序见规范 8.1）：根 index → 模块 overview → 功能 PRD → 全局规范 / 跨模块流程，不整目录加载。
- **待确认标记必须求证**：检索到 `<!-- 待确认：... -->` 标记时向用户求证，禁止把未确认内容当作既定规则自行补全。
- **修改须经人审核**：不得仅凭代码实现自动认定所有行为都是正确的产品需求；正式业务规则的修改由产品负责人确认（个人项目即用户本人）。
