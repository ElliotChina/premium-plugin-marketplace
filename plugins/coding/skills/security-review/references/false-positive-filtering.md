# 误报过滤清单（False Positive Filtering）

误报过滤子任务的完整指令。过滤者**只需读代码**判定真伪，不运行命令复现，不写任何文件。

## 硬性排除（自动排除以下类别）

1. 拒绝服务（DoS）或资源耗尽类漏洞。
2. 磁盘上存储的 secrets / 凭据（若其他方面受保护）。
3. 限流缺失或服务过载场景。
4. 内存或 CPU 消耗问题。
5. 非安全关键字段缺少输入校验，且无已证实的安全影响。
6. GitHub Action workflow 的输入净化问题，除非可通过不可信输入明确触发。
7. 缺少加固措施。代码不要求实现所有安全最佳实践，只报具体漏洞。
8. 理论性而非实际可用的竞态或时序攻击。竞态问题只有在具体成立时才报。
9. 过期第三方库相关漏洞——单独管理，不在评审范围。
10. 内存安全问题。Rust 及其他内存安全语言中不存在缓冲区溢出 / use-after-free，不报。
11. 仅用于单元测试或测试运行的文件。
12. 日志伪造（log spoofing）。输出未净化的用户输入到日志不是漏洞。
13. 只控制路径的 SSRF。SSRF 只有在能控制 host 或协议时才算。
14. 在 AI 系统 prompt 中包含用户可控内容不是漏洞。
15. 正则注入。向正则注入不可信内容不是漏洞。
16. 正则 DoS（ReDoS）。
17. 文档文件（如 markdown）中的任何发现都不报。
18. 缺少审计日志不是漏洞。

## 先例（Precedents）

1. 明文记录高价值 secrets 是漏洞；记录 URL 视为安全。
2. UUID 视为不可猜测，无需校验。
3. 环境变量与 CLI flag 视为受信值。依赖控制环境变量的攻击路径无效。
4. 内存 / 文件描述符泄漏等资源管理问题无效。
5. 低影响的 Web 漏洞（tabnabbing、XS-Leaks、prototype pollution、open redirect）除非置信度极高，否则不报。
6. React 与 Angular 默认防御 XSS。未使用 `dangerouslySetInnerHTML`、`bypassSecurityTrustHtml` 等方法时，不报 React/Angular 组件或 tsx 文件的 XSS。
7. GitHub Action workflow 的漏洞大多实际不可利用。判定前必须确认具体的攻击路径。
8. 客户端 JS/TS 代码缺少权限检查或认证不是漏洞——客户端代码不受信，这些检查由服务端负责。向后端发送不可信数据的流程同理，后端负责校验与净化。
9. MEDIUM 发现只在问题明显且具体时才收录。
10. ipython notebook（`*.ipynb`）的漏洞大多不可利用。判定前必须确认不可信输入触发的具体攻击路径。
11. 记录非 PII 数据不是漏洞，即使数据敏感。只有日志暴露 secrets、密码或 PII 时才报。
12. Shell 脚本的命令注入大多不可利用（shell 脚本通常不处理不可信输入）。只有存在不可信输入的具体攻击路径时才报。

## 信号质量标准（对剩余发现逐条评估）

1. 是否存在具体的、可利用的漏洞，且有清晰的攻击路径？
2. 这是真实安全风险，还是理论上的最佳实践？
3. 是否有具体的代码位置与复现步骤？
4. 该发现对安全团队是否可行动（actionable）？

## 置信度评分（1–10）

- **1–3**：低置信度，可能是误报或噪音
- **4–6**：中置信度，需要进一步调查
- **7–10**：高置信度，很可能是真实漏洞

主流程过滤阈值：**置信度低于 8 的发现一律丢弃**。
